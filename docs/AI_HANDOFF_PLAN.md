## 2. 最终产品目标

用户在一个交互界面输入自然语言任务，例如：

- “SAL-ORD-2026-00023 什么时候能做完？”
- “这单缺料了，给我几套采购方案。”
- “这个工单有质量异常吗，会不会影响交付？”
- “客户要求提前交货，能不能给出可执行方案？”

系统应当：

1. 识别当前业务对象和用户目标。
2. 检查客户、物料、数量、订单号、工单号等信息是否齐全；缺信息时先追问，不猜测。
3. 由协调运行时按需调用报价、采购、跟单、质量文档四个业务智能体。
4. 从 ERPNext 和 OpenMES 读取事实，并保留来源系统、记录编号、时间和调用链。
5. 对缺料、延期、质量异常等问题形成可执行方案，而不是只返回一条报警。
6. 涉及真实写入时先生成待审批动作，由人工批准后写入，再回读验证并保证幂等。
7. 用一条可追溯的业务时间线返回结论、证据、数据缺口、风险和下一步。

协调者是运行时调度层，不是第五个业务智能体。四个固定业务智能体保持不变；Leader、Partner 等是协作协议中的动态角色，不新增业务身份。

## 3. 目标架构

```text
用户输入
  ↓
会话与业务任务识别
  ↓
协调运行时
  ├─ 读取能力注册表
  ├─ 检查缺少的输入
  ├─ 动态调用四个业务智能体
  └─ 汇总事实、方案和证据
  ↓
审批门禁（仅在需要真实写入时进入）
  ↓
ERPNext / OpenMES 适配器
  ↓
回读验证、幂等检查、运行记录和业务时间线
  ↓
前端回答、方案卡片、待办和状态
```

四个智能体的职责边界：

| 智能体 | 负责的判断 | 主要数据 | 可以协作的对象 |
|---|---|---|---|
| 报价 | 客户需求、价格、成本、交期和报价方案 | ERPNext 客户、物料、BOM、价格、库存；MES 排程 | 采购、跟单 |
| 采购 | 净需求、缺料、供应商方案、采购风险 | ERPNext 库存、供应商、采购价格、MOQ、交期；MES 物料需求 | 报价、跟单、质量文档 |
| 跟单 | 工单进度、ETA、延期风险、发运条件 | ERPNext 销售订单和到货；MES 工单、批次、报工、排程、质量状态 | 采购、质量文档、报价 |
| 质量文档 | 质量资料、NCR、检验、批次追溯、资料完整性 | MES 质量问题、检验、工程文档、批次；ERPNext BOM、材料、供应商 | 跟单、采购 |

## 5. 第一优先级：先建立稳定的“任务型协同问答”

### P0-1 统一会话与业务任务

当前问答请求主要按单次问题处理。下一步增加持久化的 `assistant_session` 和 `business_task` 概念：

- `session_id`：一次连续对话。
- `task_id`：一次业务任务，例如某个报价、销售订单或工单的处理链。
- `entity_context`：客户、物料、数量、交期、ERP 订单号、MES 工单号、报价号、采购方案号等已确认实体。
- `active_plan_id`：当前正在讨论的采购或加急方案。
- `pending_approval`：等待人工确认的动作。
- `last_evidence`：上一轮已取得的真实记录和来源。

验收：用户先问“这单缺料怎么办”，再问“选第二个方案”，系统能够沿用上一轮方案；用户说“数量改成 3000”，系统能指出影响的报价、采购方案和交期，并在缺少确认信息时追问。

### P0-2 增加确定性的输入槽位检查

协调者调用大模型前后都要检查必填输入：

- 报价：客户、物料、数量、交期。
- 采购：报价或订单、BOM、库存、缺料范围。
- 跟单：ERP 订单号或 MES 工单号。
- 质量：工单号或质量问题号。

缺少字段时返回“需要补充什么、为什么需要、补充后会调用哪个智能体”，不使用固定数字，不把自然语言中的编号误当数据库数字 ID。

### P0-3 统一业务对象关联

为报价、销售订单、采购方案、MES 工单、质量问题建立可追溯关联。每次调用链都应能回答：

- 当前处理的是哪一项业务任务。
- 本次调用读了哪个 ERP/MES 记录。
- 哪个智能体产生了这个判断。
- 当前是否等待审批。
- 写入后回读得到什么。

### P0-4 默认入口和错误反馈

真实业务页面打开后优先展示“协同问答”，订单八步流程作为可视化执行面板保留。调用期间显示当前步骤、调用对象、技能、耗时和失败原因；协调者不可用时明确返回配置或连接问题，不返回固定话术。

### P0-5 能力注册表与写入隔离

逐步把协调者的技能目录改为从 AIP/ACS 注册信息构建，同时保留服务端允许列表。每项能力必须声明：

- 输入和必填字段。
- 输出结构。
- 数据来源和权限。
- 是否只读。
- 是否需要人工审批。
- 失败和数据缺失状态。

大模型不能直接获得写入工具；所有写入动作继续由后端审批端点控制。

## 6. 第二优先级：从“提问触发”扩展到“事件触发”

在 P0 稳定后，再增加业务事件协同：

1. 质量异常事件 → 质量文档智能体分析 → 跟单智能体评估交期 → 采购智能体检查供应商风险。
2. 关键物料短缺事件 → 采购智能体生成方案 → 报价智能体评估成本 → 跟单智能体评估交期。
3. 生产进度低于计划 → 跟单智能体预警 → 报价智能体重新评估客户承诺 → 人工决定是否通知客户。
4. 质量门禁未通过 → 禁止发运 → 生成待办和处理路径，不自动修改质量状态。

事件处理必须具备事件编号、去重键、重试上限、失败记录和人工接管入口。事件协同不能绕过审批门禁。

## 7. 第三优先级：质量资料和主数据完善

这部分先做能力核对，再做实现：

- 核对 OpenMES 是否存在 SOP、Control Plan、检验、批次和质量放行对应 API。
- 对没有官方 API 的能力返回 `NOT_SUPPORTED` 或 `DATA_MISSING`，不从其他 MES 猜字段。
- 明确 PPAP、IMDS、检测报告是读取、生成草稿、归档还是写回。
- 为物料建立工艺模板、产品类型和工序主数据；没有工艺模板时，报工必须阻断并指向补录位置。
- 供应商质量评分只能使用真实可关联的质量记录；没有供应商关联字段时，不要从时间或名称推断。

## 8. 每个阶段的执行模板

后续 AI 每完成一个任务，都按以下顺序工作：

1. 先读本文件、当前状态文档和相关代码。
2. 写出本阶段使用的真实字段、接口和边界；未知项先停下调查。
3. 先补测试或契约，再实现最小改动。
4. 运行后端测试、前端测试和构建；涉及真实系统时做只读检查或经过批准的审批写入。
5. 写入后回读并检查幂等；记录真实编号、状态、来源和限制。
6. 更新 `docs/current_status_and_fix_plan.md`，追加阶段小节，不覆盖历史证据。
7. 同步更新 `docs/demo_script.md` 或本文件中的验收标准。
8. 检查未跟踪文件、凭据和日志，再提交代码。

阶段完成的最低证据：

- 修改文件清单。
- 测试命令和实际结果。
- 真实接口路径、状态码和关键返回字段。
- 如果有写入：审批号、写入记录号、回读结果和幂等结果。
- 已知缺口和下一步。

## 9. 绝对边界

- 不得把 Mock、fixture、`DEMO_*` 或 `synthetic_demo_only` 当作真实业务结果。
- 不得猜测 OpenMES 字段、接口、工厂规则、价格折扣、交期公式或质量判定。
- 不得把 `data count=0` 解释为认证失败；它表示接口成功但当前没有记录。
- 不得让协调者直接写 ERP/MES。
- 不得把 ERP 草稿说成正式订单，不得把建议方案说成已批准。
- 真实写入必须有人工审批、真实身份、回读验证和幂等保护。
- 不得在文档、日志、提交或聊天中输出 Token、密码、API Secret、Cookie 或 `.env` 内容。
- 不得删除历史业务数据或用删除数据掩盖接口问题。
- 不得在没有用户确认业务规则时加入数量折扣、供应商评分、固定交期或自动承诺客户等逻辑。

## 10. 完成定义

当以下条件全部满足，才可以把本项目称为“可交给其他人继续运行的四智能体真实业务 MVP”：

1. 用户可以用自然语言连续完成一个任务，不需要每句话重复订单号和上下文。
2. 协调者能根据缺少的信息主动追问，并按需调用四个业务智能体。
3. 所有结论都能追溯到 ERPNext/OpenMES 记录或明确的数据缺口。
4. 缺料、质量异常、延期和加急场景能形成多个可执行方案。
5. 写入始终经过人工审批、回读和幂等检查。
6. 真实业务页面、Mock 回归页面和测试数据边界清楚。
7. 后端测试、前端测试、构建、页面走查和真实接口验证均有当前文档证据。
8. 文档中没有把历史计划、局部验证或测试数据写成生产能力。
