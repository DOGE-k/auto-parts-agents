# PPAP 操作指南

更新日期：2026-10-15。业务设计见[PPAP 编制业务设计与实施说明](PPAP编制业务设计与实施说明.md)，实现与验证记录见[当前状态与整改计划](current_status_and_fix_plan.md)。

## 1. 功能与适用边界

第四个质量文档智能体以 PPAP 为主。入口为「质量中心 → PPAP 编制」，负责整理来源资料、编制草稿、发现缺项和冲突、管理审核及版本。原有质量问题登记、NCR 处置/解决/关闭、质量待办、协同事件和发运规则继续保留。

当前使用 `internal-default-ppap-v1` 项目自定义模板，目录含 22 个条目，工作簿包含概览、提交清单、条目表、缺项冲突清单及来源索引。目录中的条目不等于全部必须提交，也不表示已经提供实物或原始批准文件。最终适用性由业务人员按客户要求确认。

PPAP 只写项目业务库的 8 张 `ppap_*` 表及受控文件目录，不向 ERPNext/OpenMES 写入。上游系统在此流程中只提供资料；PPAP 内部批准、客户接受、NCR 关闭和可以发运是四个不同结果，不能互相代替。

任务创建时选择数据模式，创建后不可切换。页面「任务范围」默认显示正式任务；查找功能测试种子时，选择「测试任务」，也可选择「全部任务」。

| 模式 | 可用范围 | 限制 |
|---|---|---|
| 正式任务（REAL） | 录入实际资料、按明确关联读取来源、编制、内部审核、归档及记录实际客户处理 | 拒绝明确标记的合成测试资料、不支持的来源类别和测试资料包 |
| 测试任务（TEST） | 使用本地测试资料进行编制、内部审核和归档 | 不能关联真实 ERP/MES 对象、执行真实取证或登记客户提交/接受/退回状态；产物不能用于正式任务 |

测试任务的页面和工作簿各表均显示测试标识；内部审核通过也不改变其测试属性。名称中普通的「检测」「试验测试」文字不作为合成资料的判定依据。

## 2. 升级现有部署

先备份业务数据库和 PPAP 文件目录，再停止应用后端。使用该部署实际使用的 Python 环境安装当前后端依赖，并执行迁移。现有项目 conda 环境的命令如下，默认在仓库根目录 PowerShell 执行：

```powershell
Set-Location .\backend
& '..\.conda-env\python.exe' -m pip install -e .
& '..\.conda-env\python.exe' -m alembic upgrade head
Set-Location ..\frontend
npm.cmd install
npm.cmd run build
Set-Location ..
```

其他部署环境将 Python 路径换成自身后端虚拟环境；不要为了迁移切到未配置的系统 Python。迁移 `f7b3c81d5e42` 增加 8 张 PPAP 表，后续迁移 `a8c4d12e9f60` 增加正式/测试模式并将有明确合成标记的旧任务归为测试任务。当前迁移目标为 `a8c4d12e9f60`。启动应用不会替已有数据库自动完成迁移。

规格冲突、模式隔离、排版修复及本次输入辅助没有新增第三方依赖。本次输入辅助也没有新增数据库迁移，迁移目标仍为 `a8c4d12e9f60`。已经安装当前 PPAP 依赖的环境不必重新下载全部依赖；尚未安装 PPAP 的旧部署仍需按上述步骤安装，其中包括 `openpyxl>=3.1,<4.0`。更新代码后需重启后端；前端使用开发服务时刷新页面，使用部署构建时重新构建并更新静态文件。

输入保存反馈的调整只涉及前端，不需要安装新依赖或执行数据库迁移。已更新代码且正在运行前端开发服务时，刷新网页即可；使用静态部署时，需要先更新前端构建文件。

数据库模块会与应用共用配置加载顺序：已有环境变量 → 根目录 `.env` → `backend/.env` → 默认 SQLite。迁移日志显示的数据库类型必须与应用一致；配置 PostgreSQL 的部署应显示 `PostgresqlImpl`。旧版本直接运行 Alembic 曾跳过配置而迁移默认 SQLite，此缺陷已修复；升级时必须使用含该修复的代码。

重启后端和前端，在「系统连接」登录项目账号，再进入 PPAP 页面。所有查询和文件下载要求可识别身份；任务创建、资料确认、编制、审核等持久操作要求真实项目会话和 `quality_manager` 角色。普通操作不需要在页面另外填写本地写入令牌。

## 3. 操作顺序

### 3.0 四阶段工作台

选中任务后，任务列表自动收起；通过「切换任务」重新选择。页面顶部显示零件、图纸版本、编制状态、内部审核和客户处理，以及依据实际检查结果给出的下一步。浏览一个阶段不会把它标为完成，输入条数也不表示资料完整。

| 阶段 | 处理内容 |
|---|---|
| 确认要求 | 任务信息与明确关联；逐项确认提交、保留、按要求提供或不适用的依据 |
| 准备资料 | 「录入资料」按类别填写；「来源资料」查看取证、登记原件与批准包引用 |
| 编制与检查 | 生成或检查草稿，优先查看当前待补项；展开已登记问题、条目内容及版本对照 |
| 审核与归档 | 明确当前版本，核对不可审核原因，人工提交、批准或退回；批准版归档 |

「来源与操作记录」是各阶段都可打开的辅助入口，保留运行、来源、调用链、步骤及任务留痕。客户实际处理单独展开；测试任务不能登记正式客户状态。页面只使用当前已取得的事实：检查或版本一致性尚未读取时显示待核对，不显示为零问题或已经批准。

录入资料按以下类别组织，全部 13 类原有输入契约继续保留。表单「资料类型」可以直接选择完整列表。

| 资料类别 | 资料类型 |
|---|---|
| 基础与客户要求 | 产品基础信息、客户要求、工程变更、客户处理要求 |
| 工艺与工程 | 工序清单、工序关系、特性与规格 |
| 检验与研究 | 检验原始值、MSA 原始研究、过程研究、材料与性能资料 |
| 设备与实物 | 设备与包装、实物记录 |

同一任务、同一侧别在类别间切换会保留未提交的录入草稿；切阶段不清空研究表格，包括尚未修正的非法单元格。需要切任务时先保存或明确「清除当前录入草稿」。清除只处理当前浏览器中的未提交内容，不删除已保存记录；修订记录时恢复原已保存值。非法研究值须先修正后才能切换资料类型。仍有保存回读待确认时，只能返回并重新读取，不能切任务或重新提交。

已确认输入只展示当前资料类型的记录，先显示中文字段摘要、来源、确认人和时间；「原始记录」保留完整结构。记录标识及来源类型放在「记录标识与来源详情」，修订仍沿用原记录键。首次输入无须自行编造记录键。

本轮为前端调整，没有新增依赖、后端接口或数据库迁移。本机开发服务运行时刷新网页即可；静态部署需要更新前端构建文件。

### 3.1 建立任务和确认适用性

1. 先选择正式或测试模式，再填客户、零件编号、名称、图纸版本、变更等级、提交原因及等级等已确认信息；不知道的字段留待补充，不能套用旧样例。测试资料另建测试任务，不能通过改名或修改来源类别转为正式资料。
2. 左件和右件分别建立任务并标明 `LEFT` / `RIGHT`。只用于双方共用的确认记录才使用 `BOTH`，左右敏感的测量记录不能使用无侧别记录替代。
3. 正式任务可编辑明确工单、订单、报价或质量问题关联编号。缺少关联键时，对应来源会显示跳过，不自动找一个其他对象补上。测试任务的这些关联字段不可填写。
4. 逐项选择「提交 / 留存 / 按要求提供 / 不适用」。建议值需要人工确认；选择不适用必须写客户规则或工程依据。未确认适用性会阻断批准。

### 3.2 获取资料和补录输入

进入「准备资料 → 来源资料」。正式任务查看取证计划，再请求批量取证。后端按关联键自动读取可取得的资料，记录真实读取/派生步骤，并将结果分成以下三种。测试任务不执行真实取证，使用明确来源的本地测试资料。

| 结果 | 含义 | 下一步 |
|---|---|---|
| OK | 接口成功且取得资料 | 核对范围、版本及内容；分页截断仍不算完整 |
| EMPTY | 接口成功，但该来源没有数据 | 补充资料，不表示认证失败或不适用 |
| ERROR | 接口或关联读取失败 | 修复连接、权限或关联后重试，不表示没有此项 |

父来源读取失败时，其子来源也记录失败；不会把未取得的检验/文档列表标成合法空数据。运行记录可以查看调用链与跳过原因。

客户原件当前通过「登记原件或引用已批准包」登记：

- 已有文件先由维护人员放入受控目录，页面填写相对路径；外部文件编号可以登记，但未读取实际内容时不计有效证据。当前页面没有文件上传控件，也不会把填写路径当作已上传。
- 指定文件编号、资料说明，并明确勾选该原件对应的条目。设计原件还须填写实际文档版次，内容指纹不能代替图纸版本。空绑定只登记来源，不计任何条目的就绪；不要把一份无关文件勾为所有条目的依据。
- 引用既有批准包填写产物 ID，系统核对批准状态、实际文件及哈希；引用不等于已经取得客户批准。测试包和正式包不能互相引用；嵌套引用同样核对各版本的来源快照。历史包若无法核对原输入及指纹，需要重新编制，不能按当前资料推断历史来源。

进入「准备资料 → 录入资料」，「工程与检验输入确认」提供 13 类数据集的字段契约。填来源引用并点击「确认并保存输入」后才持久保存；保存人取登录会话身份。可选字段支持明确 `null`，与未提供字段分开；数值字段不接受布尔值或伪造合格结论。

#### 3.2.1 识别已有资料，减少重复填写

选择数据集及侧别后，页面只读检查本任务已登记的信息，提供有来源的填充建议：

- 产品基础信息可识别本任务已登记的客户名称、零件编号与名称、图纸版本和变更等级。每个建议字段显示来源；任务元数据引用不等于客户原件。
- 检验、MSA 和过程研究可从同侧、已确认且唯一的特性记录识别编号、单位及该数据集允许的规格字段。多个候选时在「从已确认特性选择」明确选择；重复或矛盾规格不用于预填。
- 建议只填空字段，保留人工填写、人工清空及明确 `null`。载入修订时保留原记录内容，不用其他记录的测量值填补缺测。
- 测量记录的「来源引用」仍需填写实际检测资料的来源。特性规格的来源单独显示在字段旁，不能代替本次测量来源。方法、公差、验收阈值、原始样本、签字及结论不会自动生成或复用。

识别结果先留在表单中，核对后点击「确认并保存输入」。识别失败会显示错误，不能据此判断没有资料。此处识别已有结构化信息，不做图片文字识别、文件解析或新的 ERP/MES 自动采集；正式任务的原有取证流程仍按明确关联执行。

#### 3.2.2 表格录入原始检测数据

MSA 的「评价人 × 零件 × 测次原始数据」、过程研究的「原始样本序列」和「原始子组」已提供表格编辑，不再要求普通操作人员手写数组：

1. 已确认输入点击「载入修订」后，表格识别原有评价人、零件标识、重复测次、样本数量和子组边界，保留原始顺序。
2. 新研究按实际方案使用「新增评价人」「新增零件」「增加测次」「新增原始样本」或「新增子组」。没有资料时保持空表，不预设固定采集方案，也不自动补齐不同记录的测次。
3. 单元格填写原始有限数值；空格表示缺测并保存为 `null`，不能当成 0。非法数值会标记，修正前不能保存；新增行不会代填测量结果。
4. 单独维护样本序列和子组；两者是否逐项一致仍由编制检查确认，页面不自行拆分、重排或制造子组。
5. 「高级 JSON」保留原始结构核对入口。未识别结构原样保留，不强行转成表格或丢弃字段，保存仍需通过后端输入契约。

表格识别的是已录入的数据结构，不代表研究方法、样本量或客户规则已经批准。填写来源、方法及必要基准后，仍需确认保存并重新编制。

同一任务、同一特性编号、同一侧别只允许一条特性规格记录。修改规格时载入原记录并使用原记录键保存；换一个记录键重复添加同一特性，即使数值相同也会被拒绝，原输入不会被覆盖。历史重复记录、规格上下限冲突和单位缺失/冲突会保留各记录的来源，形成阻断项；系统不会任取其中一条来给出合格结论。

#### 3.2.3 确认输入是否已保存

保存状态显示在「确认并保存输入」按钮附近，不需要返回页面顶部查看提示。

| 页面反馈 | 含义与处理 |
|---|---|
| 尚未确认保存 / 有修改尚未保存 | 当前表单内容尚未提交，或保存后又作了修改；自动识别和载入修订本身不写入 |
| 正在保存 | 保存按钮显示「正在保存…」并禁用；等待结果，不重复点击 |
| 保存成功，已回读确认 | 服务端写入后，页面已读取并核对对应记录；显示记录键、侧别和已确认条数，自动展开「已确认输入」并突出显示本次记录 |
| 保存请求已成功，但记录回读未完成 | 保存请求已经成功，后续读取失败或记录尚未核对；保留表单，点击「重新读取已保存记录」，不要再次提交 |
| 保存结果未确认 | 网络中断或服务异常，不能据此判断是否已写入；先点击「重新读取已保存记录」核对，避免重复提交 |
| 保存失败 / 请补充或修正 | 显示本地必填校验或明确业务拒绝的原因，并保留已填内容；按原因修正，核对后再提交 |

「重新读取已保存记录」只重新查询，不执行保存。回读成功时，列表中的来源、确认人和确认时间均取已保存记录；缺失或不一致时继续保留未确认提示，不把读取失败当作未写入。等待回读确认期间，保存按钮保持禁用。

首次保存新记录增加条数；载入原记录进行修订通常不增加条数，应查看突出显示的记录和最新内容。保存后继续编辑会提示「有修改尚未保存」，已确认列表仍保留上一次保存的内容，新的表单值需要再次确认保存。

### 3.3 编制、检查和修正

点击编制后，依次生成草稿、运行 12 类一致性检查、同步缺项冲突、输出 Excel，再保存运行和版本。编制状态为 `BLOCKED` 时仍可下载草稿查看问题，但不能批准。

「缺项与补录位置」在未编制时也显示实时检查结果，可按阻断项/全部发现、条目和责任岗位筛选。实时发现与已登记未处理问题分别统计，不能把未保存的检查发现当成持久问题记录。

点击「去补充」定位服务端明确提供的数据集、原记录、适用性、任务信息或证据登记位置。修订原记录保留记录键、来源类别、来源引用、侧别和明确 `null`；定位及载入本身不保存。规则未确认或无法确定唯一补录位置时只说明原因，不伪造可编辑入口。补录后确认保存，再回到「编制与检查」重新检查或编制。

缺项同时显示影响条目、字段、依据和补充资料。`RESOLVED` 表示数据修正后已不再检出；仍检出的发现不能直接改成已解决。`WAIVED` 记录人工接受理由，不能绕过尚存在的阻断项；重新检查仍检出时会重开。

计算器不会生成检测数据：

- 尺寸比对保留原始值和单位；只有唯一、同侧别且一致的规格才能参与比对。重复规格、检验记录与特性规格冲突、单位缺失或不一致均阻断审核，不自动换算或选择某一条规格。缺规格/缺值/尺寸异常保持待补。
- MSA 当前仅实现明确选择的平均极差法；不支持的方法明确报未实现。
- 过程能力区分组内变差的 Cp/Cpk 与总体样本变差的 Pp/Ppk。子组展开必须与原始样本逐项一致；零变差不返回无穷大。
- 判定只使用已确认的规则。公开参考区值只展示参考意义；无确认人、未确认阈值、缺指标或未达标不会成为已完成提交资料。

相同输入、规则及编制器版本重复编制返回原运行及版本。输入、适用性、来源绑定、负责人、审核人或期限变化需要重新编制；编制器/导出器升级后也生成新版本，不覆盖历史文件。同一显式请求键不能用于不同快照。失败运行不会变成批准文件，修复后使用新的显式请求键受控重试。

「版本修改对照」默认比较当前已登记资料与最新编制版本，也可在「对照版本」指定历史版本。表格列出数据集、记录键、侧别、变化字段、原值、新值和各自来源，并说明受影响条目。数组可展开查看完整原值；未提供、明确 `null`、空字符串与历史未保存原值分别显示。历史快照没有完整内容时不会从当前记录猜旧值。对照只读，不刷新远端、不修改输入或批准版；修改资料后仍须生成并审核新版本。

当前导出器为 `ppap-internal-xlsx-1.1`。长说明按列宽换行，并在单行容量不足时分成连续行，保留完整内容。26 张工作表仍可编辑；测试包每张表显示测试标题及打印页脚。下载后修改的副本不等于系统受控产物，不能替换审核所指向的文件。

### 3.4 审核、归档和客户记录

1. 提交审核前检查最新草稿、输入及规则快照、实际文件哈希和零阻断。
2. 登录人员填写意见后批准或退回。审核人由会话决定，不能在请求体中冒填；相同账号编制/审核会显示岗位分离提示，当前尚未强制两人分离。
3. 批准对应具体文件版本和快照，该版本冻结。资料修改只能产生新版本；旧审核请求不能改变新版本状态。
4. 已批准版本可以归档。归档旧版本不会把当前新草稿标为已归档。
5. 正式任务内部批准后，按实际客户记录登记「已提交 / 已接受 / 已退回」及引用依据。测试任务可验证内部审核及归档，但不能登记这些客户状态。系统不自动获取客户回复，不代客户签字。

已归档文件仍保留编制时的内容；内部审核及客户处理决定在任务/审核记录中查询，不回写文件中的签字或合格结论。

## 4. 存储、备份和规则配置

默认文件目录为 `backend/data/ppap_store`，可通过 `PPAP_STORAGE_DIR` 指定其他受控绝对目录。生成包使用独立任务/版本路径；下载核对路径边界和文件 SHA-256。原件发生变化或丢失时，审核会拒绝旧证据，应重新登记并编制。

规则文件默认在受控目录的 `acceptance_rules.json`，可用 `PPAP_RULES_FILE` 指定。其结构包括 `rule_version`、`source`、`confirmed_by`、`confirmed_at` 和 `metrics`。指标规则支持已确认的 `min` / `max` / `conditional_max`；具体指标、方法与阈值仍需业务方给出，部署时不填一套猜测值。条件接受也不能直接替代正式偏差依据。

备份应同时包含业务数据库（任务、来源、输入、运行、审核和文件索引）及整个 PPAP 文件目录。建议停止 PPAP 写入后制作同一时间点的备份，再恢复到隔离环境核对任务/版本数量和文件指纹。只复制 Excel 会丢失审计和快照，只复制数据库会丢失文件。数据库凭据、原件、数据库和生成包均不得提交 Git。

本版没有自动清理或保存期限策略，等待业务方确认；`backend/data/` 已被仓库忽略。使用自定义目录时，部署方同样需要限制访问并排除 Git 跟踪。

维护接口时，创建请求与任务列表筛选使用字段 `mode`（`REAL` / `TEST`），任务响应与数据库字段使用 `data_mode`。不要在创建请求中用响应字段代替 `mode`；更新接口不接受模式切换。
