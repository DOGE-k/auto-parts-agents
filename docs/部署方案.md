# 部署环境可复现部署方案

## 目标

让使用者从 GitHub 获取项目后，在自己的 Windows 电脑上启动，并能看到与当前项目一致的页面结构、AI 协同问答入口和业务流程。

“能启动页面”和“复现当前真实 ERPNext/OpenMES 环境”是两个不同目标，必须分开验收。

## 当前仓库为什么还不能直接达到目标

当前仓库的 `启动应用.bat` 主要用于已经准备好的开发机：

1. `services/` 下的 ERPNext/OpenMES 源码是独立上游仓库，被 `.gitignore` 排除，不会随 GitHub 克隆得到。
2. `APP_ADAPTER_MODE=real` 依赖每台机器自己的 ERPNext API Key、OpenMES 会话/集成凭据、写入门禁令牌和可选的 DeepSeek Key。
3. 真实凭据不能复制到 GitHub，也不能把当前机器的 `.env` 发给使用者。
4. 当前启动脚本会检查环境并启动服务，但不会把 Python、Node、Docker、上游仓库、ERPNext 建站和业务初始化全部封装成真正的无前置一键安装器。
5. `APP_ADAPTER_MODE=mock` 可用于本地验收，但数据会标记为 `MockERP`、`MockMES`、`synthetic_demo_only`，部分质量文档、检验、批次和写回能力不等同于真实环境。

## 方案 A：使用者体验版（推荐先做）

### 目标

每台电脑独立启动一个安全的验收环境，展示统一的页面、导航、协同问答交互和预置业务故事，不依赖使用者访问当前机器的 ERPNext/OpenMES，也不暴露任何真实凭据。

### 必须实现

- 增加明确的 `demo` 配置档，不再使用 `auto` 静默切换。
- 使用项目内置 Mock 适配器和 SQLite 验收库，准备固定、可重置的测试数据。
- 页面显式显示“本地测试数据”，不把验收结果称为真实 ERP/MES 结果。
- 增加一个可复现的启动入口：检查 Python/Node，安装项目依赖，生成本机 `.env.demo`，启动后端和前端，执行健康检查。
- 为协同问答提供不含密钥的业务验收路径；若需要真实 LLM，自行填写使用者自己的 API Key，不能把你的 Key 写入仓库。
- 提供“重置测试数据”操作，确保每位使用者重新开始时结果一致。
- 关键验收：健康接口、首页、协同问答、报价/采购/跟单/质量页面、刷新和重置流程均能完成。

### 不能宣称

这个版本只能称为“可复现验收版”。它不能作为真实 ERPNext/OpenMES 已部署、真实数据已接通或真实写回已验证的证明。

## 方案 B：真实复现版

### 目标

每台电脑都运行一套自己的 ERPNext、OpenMES、业务后端和前端，并通过种子脚本准备同样的业务主数据和测试记录。

### 必须实现

- 固定并记录 ERPNext/OpenMES 上游版本和 compose 配置。
- 提供环境检查：Docker Desktop、Compose、Python 3.12/3.13、Node 20+、端口和磁盘空间。
- 一键克隆上游仓库、生成本机配置、启动两个 compose 项目、等待健康状态。
- 自动完成 ERPNext `localhost` 建站和 OpenMES 首次初始化，或明确把一次性人工步骤列出来。
- 所有种子脚本改为可重复执行，并在每一步完成后检查结果；不能重复创建脏数据。
- 为每台机器生成本地随机写入门禁令牌；ERPNext/OpenMES/LLM 凭据由使用者自己填写。
- 完成真实模式验收：健康接口、身份解析、ERPNext/OpenMES 连接、协同问答、只读业务链和审批门禁。
- 至少在一台干净 Windows 电脑上从 GitHub 克隆后完整重放，才能在文档中写“可部署”。

### 现实边界

真实复现版安装和启动更重，首次准备时间也更长；它复现的是同样的系统结构和种子业务数据，不是共享当前机器的数据库。若要所有人看到同一份实时数据，应改为部署一套集中式服务，让使用者通过网络访问，而不是每人本地部署。

## 两个版本都不能做的事

- 不提交 `.env`、ERPNext API Secret、OpenMES Token、DeepSeek Key、证书或 Cookie。
- 不把 `auto` 模式的 Mock 回退结果当成真实数据。
- 不把固定 fixture 改名后当成真实工厂记录。
- 不在没有确认平台要求和真实地址前修改 ACS 中的 `TBD-*`、`example.com` 或 `localhost` 占位值。

## 实施顺序

1. 先决定使用者要使用方案 A 还是方案 B。
2. 先完成所选方案的本机启动、健康检查和关键页面验收。
3. 在一台没有项目环境的 Windows 电脑上从 GitHub 重放。
4. 根据重放结果补充错误提示、安装说明和重置步骤。
5. 再提交代码、更新 README，并把 GitHub 链接交给使用者。

## 完成判定

只有当使用者能在自己的电脑上按 README 完成启动，并且实际打开页面、发起协同问答、查看业务结果和重新启动后仍能复现，才算达到“部署环境也能部署”。
