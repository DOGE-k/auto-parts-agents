# 统一项目身份与 ERP/MES 写入权限设计

> 状态：已实施基础版本（本次提交）；角色细化、审计字段扩展和部署验收仍按本文继续推进
>
> 更新时间：2026-10-05

## 1. 目的

当前页面把 OpenMES 用户会话作为“审批账号”。这样可以完成现有的审批和真实写入，但使用者需要理解 OpenMES 登录、ERPNext 服务端凭据和本地写入令牌三个概念，系统的身份边界不够清楚。

本方案把人工操作者的身份收回到本项目：用户只登录本项目账号，登录后才可以执行审批和写入 ERPNext、OpenMES 的操作。ERPNext 和 OpenMES 的账号只作为后端连接上游系统的服务身份，不再作为页面上的人工审批账号。

## 2. 现状与问题

### 2.1 当前身份链路

当前实现大致是：

```text
页面登录 OpenMES
        ↓
浏览器保存 OpenMES Bearer 会话
        ↓
后端从会话解析 OpenMES 用户和角色
        ↓
审批接口使用该身份检查权限
        ↓
后端通过 ERPNext/OpenMES 适配器执行写入
```

当前还有两类后端凭据：

- ERPNext API Key/Secret：后端读取 ERPNext，并在审批通过后创建 ERP 草稿；
- OpenMES 集成 Token/API Key：后端读取或调用 OpenMES 的集成接口。

此外，`REAL_WRITE_API_TOKEN` 是本机写入门禁令牌，用于阻止未启用真实写入的环境直接调用外部写接口。它不是用户密码，也不应充当人工身份。

### 2.2 需要解决的问题

1. 页面显示的是 OpenMES 账号，使用者容易误以为必须分别登录 ERPNext 和 OpenMES。
2. ERPNext 和 OpenMES 的服务凭据与人工审批身份没有在产品概念上完全分开。
3. 审计需要同时回答两个问题：谁在项目中批准了操作，以及后端通过哪个上游服务身份执行了写入。
4. 写入权限应由一个项目级登录状态统一控制，而不是让每个上游系统各自承担页面登录职责。

## 3. 目标架构

### 3.1 身份分层

```text
项目用户（人工身份）
        │
        │ 项目登录会话
        ▼
业务平台后端
   ┌────┴────┐
   │         │
ERPNext 服务身份   OpenMES 服务身份
   │         │
ERPNext API       OpenMES API
```

- **项目用户**：页面操作者，负责发起和批准业务动作，出现在审批记录和审计记录中。
- **业务平台后端**：统一做登录校验、角色校验、审批校验、写入门禁和审计记录。
- **ERPNext 服务身份**：只由后端使用，负责 ERPNext 数据访问，不作为页面登录身份。
- **OpenMES 服务身份**：只由后端使用，负责 OpenMES 数据访问，不作为页面登录身份。

### 3.2 登录后的权限规则

| 操作 | 未登录 | 已登录但无相应角色 | 已登录且有角色 |
|---|---|---|---|
| 查询业务数据 | 可继续保留只读访问 | 可继续保留只读访问 | 可查询 |
| 创建审批 | 拒绝 | 拒绝 | 允许建立审批记录 |
| 批准或驳回审批 | 拒绝 | 拒绝 | 允许，审批人取当前项目用户 |
| 写入 ERPNext | 拒绝 | 拒绝 | 必须审批通过后执行 |
| 写入 OpenMES | 拒绝 | 拒绝 | 必须审批通过后执行 |
| 读取审计记录 | 按项目角色控制 | 按项目角色控制 | 按权限读取 |

这里的“未登录不能修改”指所有 ERPNext 和 OpenMES 写接口都拒绝请求。只读页面是否也必须登录，可以作为单独的部署配置，不影响写入门禁。

### 3.3 写入链路

所有真实写入统一经过以下顺序：

```text
项目用户登录
  → 后端检查项目会话
  → 检查项目角色
  → 建立业务审批记录
  → 项目用户批准
  → 检查部署级写入开关（如已配置）
  → 使用后端服务身份调用 ERPNext 或 OpenMES
  → 回读目标记录
  → 保存项目用户、上游系统和回读结果
```

人工身份和服务身份不能互换：

- 前端提交的 `approved_by` 只能作为兼容字段，不能决定真正的审批人；
- 后端从项目会话取得审批人；
- 后端从服务器配置取得 ERPNext/OpenMES 服务凭据；
- 前端永远不接触上游服务密钥、Secret 或集成 Token。

## 4. 项目登录会话设计

### 4.1 登录接口

建议新增项目自身的登录接口：

- `POST /api/auth/login`：用户名和密码换取项目会话；
- `GET /api/auth/me`：返回当前项目用户、显示名、角色和会话状态；
- `POST /api/auth/logout`：撤销当前项目会话；
- 所有接口使用 HttpOnly、SameSite 的会话 Cookie，页面不保存服务端密钥。

密码只保存经过安全哈希处理的结果，不保存明文密码。会话应有过期时间，并支持服务端撤销。

当前实现使用根目录 `.env` 中的 `PROJECT_AUTH_USERNAME`、`PROJECT_AUTH_PASSWORD`、
`PROJECT_AUTH_DISPLAY_NAME` 和 `PROJECT_AUTH_ROLES` 在首次启动时初始化项目账号；已有账号不会被环境变量覆盖。
登录后通过 HttpOnly Cookie 保存项目会话，普通页面不再把 OpenMES 登录当作审批入口。

### 4.2 项目用户最小字段

项目用户至少需要：

| 字段 | 用途 |
|---|---|
| `user_id` | 项目内部稳定编号 |
| `username` | 登录名 |
| `display_name` | 页面和审计显示 |
| `password_hash` | 密码哈希，不保存明文 |
| `roles` | 业务角色 |
| `is_active` | 是否允许登录 |

项目会话至少需要保存用户编号、会话摘要、创建时间、过期时间和撤销状态。会话原文不写入业务审计日志。

### 4.3 角色边界

项目角色沿用现有业务能力名称，先覆盖：

- `sales_manager`：报价审批、销售订单草稿；
- `purchase_manager`：采购方案审批、采购订单草稿；
- `quality_manager`：质量处置、解决和关闭；
- `production_manager`：工单下达、报工；
- `system_manager`：用户和系统配置管理。

角色只是项目内部授权，不等同于 ERPNext 或 OpenMES 的角色。后端服务身份是否有能力执行具体上游接口，仍需单独检查并在失败时明确返回。

## 5. 审计记录

每次审批和写入至少记录：

| 类别 | 记录内容 |
|---|---|
| 项目操作者 | `project_user_id`、用户名、显示名 |
| 业务动作 | 动作类型、业务对象编号、审批编号 |
| 审批过程 | 创建人、批准人、批准时间、决定和备注 |
| 写入目标 | `ERPNext` 或 `OpenMES` |
| 上游服务身份 | 服务账号标识或配置别名，不记录密钥和 Token |
| 结果 | 请求摘要、响应摘要、回读结果、错误码和时间 |

这样可以区分“谁批准了操作”和“哪个后端服务身份实际调用了上游系统”。审计中禁止保存密码、Cookie、Bearer Token、API Secret 和完整请求头。

## 6. 页面调整

实施后页面统一使用以下概念：

- “项目登录”或“当前项目用户”；
- “当前项目审批身份”；
- “ERPNext 数据连接”和“OpenMES 数据连接”只显示连接状态，不显示为人工登录入口；
- 登录后可以在同一项目会话中执行 ERPNext 和 OpenMES 的审批、报工、质量处置等写入；
- 未登录时，所有写入按钮不可执行，并在后端保持 401 拒绝；
- “高级联调设置”只保留给部署或开发人员，不参与普通业务登录。

## 7. 迁移步骤

### 阶段一：建立项目身份基础

1. 新增项目用户、项目会话和角色数据表；
2. 新增项目登录、当前用户和退出接口；
3. 提供一次性本地初始化账号方式，初始化密码只由部署者设置；
4. 增加会话过期、撤销和密码校验测试。

### 阶段二：迁移写入门禁

1. 新增 `require_project_user` 和角色检查依赖；
2. 将报价、采购、工单、报工、质量和发运相关写接口统一切换到项目会话；
3. 审批人统一从项目会话取得，不再信任前端提交的身份字符串；
4. `REAL_WRITE_API_TOKEN` 可作为部署级兼容门禁配置，但不作为普通项目用户的登录凭据；
5. ERPNext/OpenMES 适配器继续使用后端服务凭据。

### 阶段三：迁移前端和审计

1. 删除“OpenMES 审批账号”作为普通业务入口的文案；
2. 增加项目登录状态、当前用户和角色显示；
3. 未登录时统一禁用或拦截写入操作；
4. 审计表补充项目用户和上游服务身份；
5. 更新部署指南、功能说明和验收流程。

### 阶段四：兼容与清理

1. 在迁移期间可以保留 OpenMES 登录作为受控兼容入口，但不能同时把它当作新的项目身份；
2. 完成项目账号迁移和验收后，关闭普通页面对 OpenMES 登录的依赖；
3. 清理旧文案、旧的身份回退逻辑和只适用于 OpenMES 登录的前端状态。

## 8. 验收标准

- 未登录请求任何 ERPNext/MES 写接口都返回 401；
- 已登录但无角色时返回 403，不产生上游写入；
- 一个项目账号登录后，可以在同一会话中完成 ERPNext 和 OpenMES 的审批与写入；
- ERPNext/OpenMES 的服务凭据只存在后端配置，浏览器和页面审计中不出现密钥；
- 审计记录能同时显示项目用户和实际写入的上游系统；
- 重复请求仍保持原有幂等、回读验证和审批留痕；
- 项目账号退出或会话过期后，所有写接口立即拒绝；
- 只读查询是否要求登录由部署配置明确说明，不能因身份失败而伪造空数据。

## 9. 当前实现与后续项

本次提交已完成：项目用户/会话表及迁移、`/api/auth/login`、`/api/auth/me`、
`/api/auth/logout`、HttpOnly 项目会话、普通页面的项目账号登录文案，以及主要 ERP/MES
审批和写入路由的项目会话门禁。OpenMES 登录入口已停用，ERPNext/OpenMES 凭据仍只由后端适配器使用。

仍需在目标部署环境完成：设置 `PROJECT_AUTH_PASSWORD`、执行数据库迁移、验证各角色权限和真实上游
回读，并根据审计要求补充项目用户与上游服务身份的分列记录。

## 10. 待确认项

开始改代码前，需要确认以下产品选择：

1. 初始项目账号是通过部署时环境变量初始化，还是通过首次启动向导创建；
2. 是否保留多角色，还是先只提供一个项目管理员账号；
3. 只读查询是否继续允许未登录访问；
4. 项目会话默认有效时间，以及是否需要“记住登录”；
5. OpenMES 兼容登录保留多久，何时从页面完全移除。

这些选择用于后续增强，不影响本次基础版本的统一项目登录和写入门禁。
