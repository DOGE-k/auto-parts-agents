# AIC 智能体互联比赛：梧桐接入与作品提交待办

> 项目：汽车零部件工厂智能体
>
> 适用对象：接手本项目的 AI 或开发者
>
> 当前原则：先完成可验证的梧桐平台互联闭环，再整理比赛材料。没有实际响应、截图、日志或回读证据的事项只能标为“待验证”。

## 1. 已确认的比赛要求

依据比赛规则和技术报告大纲，作品必须：

- 基于 AIP 国家标准和 AIP-PUB 开源代码完成开发；
- 落地多智能体互联交互逻辑；
- 在梧桐平台完成智能体注册、自动发现、跨端互联访问；
- 展示跨智能体双向通信；
- 在作品材料中提供平台后台访问量截图、互联交互记录和运行证据；
- 提交技术方案 PDF、验收视频、答辩 PPT、佐证材料和完整代码链接。

规则没有写死必须注册一个还是四个智能体，但评分明确考察多智能体协同、自动发现和跨智能体双向通信。因此，注册数量应以实际参与跨端验收的服务为准，不能只把本地 ACS 文件数量当成完成证明。

## 2. 当前项目事实

### 已存在

- 报价 AIP 服务：`/aip/quotation/rpc`
- 采购 AIP 服务：`/aip/procurement/rpc`
- 跟单 AIP 服务：`/aip/tracking/rpc`
- 质量文档 AIP 服务：`/aip/quality-document/rpc`
- 本地协调者可以通过 AIP RPC 调用上述四个业务智能体。
- 四个 ACS 文件位于 `backend/acs/`。

### 尚未证明

- 尚未取得梧桐平台分配的真实 AIC；
- 尚未完成梧桐平台审核、Discovery 发现和跨端访问记录；
- 当前 ACS 中仍有 `TBD-*` AIC 占位值；
- 当前 ACS endpoint 使用 `localhost:9000`，不能直接作为平台互联证据；
- 当前 provider 中存在 `example.com` 等占位信息；
- 本地协调者目前是后端调度层，不是单独暴露的 AIP RPC 入口；
- 尚未确认比赛验收由四个业务智能体分别注册，还是由一个 Leader 入口调度四个 Partner。

## 3. 推荐的目标结构

推荐目标是：

```text
梧桐平台调用
      ↓
可被平台发现和访问的 Leader / 协同入口
      ↓ AIP RPC
报价智能体、采购智能体、跟单智能体、质量文档智能体
      ↓
ERPNext / OpenMES 真实只读数据与审批门禁
```

这里的 Leader 入口是否需要新增为独立注册智能体，必须先根据实际平台接入方式确认。不能把现有前端页面或本地协调函数直接称为已注册的 Leader。

## 4. 注册表单填写口径

以下内容已经可以确定：

| 字段 | 填写口径 |
|---|---|
| 名称 | 使用项目中对应的业务智能体名称 |
| 版本 | `1.0.0` |
| 能力描述 | 使用对应 ACS 的真实职责和边界描述 |
| 是否可派生（本体） | 四个直接提供业务服务的智能体选择“否” |
| AIC | 不自行编造，审核通过后使用平台分配值 |
| provider | 使用平台验证账号能确认的真实组织和联系人信息，不使用 `example.com` 占位值 |
| endpoint | 使用平台可以稳定访问、并能按 AIP 返回结果的服务地址，不使用仅本机可见的 `localhost` |
| 证书 | 注册审核通过、获得 AIC 后，再按官方指南使用 `acps-cli` 申请 mTLS 证书 |

四个业务智能体的 ACS 文件：

- `backend/acs/quotation_acs.json`
- `backend/acs/procurement_acs.json`
- `backend/acs/tracking_acs.json`
- `backend/acs/quality_document_acs.json`

## 5. 按顺序执行的待办

### P0：先确认接入方案，禁止直接提交

- [ ] 确认比赛验收的入口：四个业务智能体分别被发现，还是新增一个 Leader 入口统一调度。
- [ ] 确认 Leader 是否需要作为独立 AIP 服务和智能体注册。
- [ ] 确认平台可访问的服务部署方式和实际 URL。
- [ ] 确认真实 provider 组织名称、部门、联系人和邮箱。
- [ ] 确认平台对 endpoint、HTTPS、mTLS 和证书 SAN 的具体要求。

**停止条件：**以上任一项没有真实资料时，不修改成猜测值，不提交注册。

### P1：准备可被平台访问的服务

- [ ] 部署或映射入口服务，使梧桐平台能够访问健康检查和 AIP RPC。
- [ ] 验证入口服务返回有效的 AIP 任务状态和结果。
- [ ] 验证入口能够调用至少两个业务智能体，形成可记录的跨智能体链路。
- [ ] 如果四个业务智能体都参与验收，分别验证四个 endpoint。
- [ ] 保存 endpoint、响应状态、调用时间和 correlation/task ID。

### P1：整理 ACS

- [ ] 保留实际名称、职责边界、输入输出模式和技能列表。
- [ ] 删除或替换 provider 中的虚假示例域名、邮箱和组织信息。
- [ ] 将 endpoint 替换为平台可访问地址。
- [ ] 不手工生成 AIC；保留平台分配流程。
- [ ] 四个业务智能体的 `is_ontology` 按“否”处理，除非平台审核人员给出不同要求。
- [ ] 用平台 ACS 示例校验 JSONC/JSON 语法和字段兼容性。

### P1：完成第一次注册闭环

- [ ] 先选择一个最完整的入口服务创建注册草稿。
- [ ] 填写名称、版本、描述、ACS 和本体选项。
- [ ] 保存草稿，记录平台返回的草稿 ID、状态和错误信息。
- [ ] 提交审核。
- [ ] 审核通过后记录真实 AIC、状态、ACS 版本和更新时间。
- [ ] 不把“保存草稿”或“提交审核”写成“已完成平台互联”。

### P1：证书、发现和跨端调用

- [ ] 按官方指南配置 `acps-cli`。
- [ ] 使用平台分配的 AIC 获取 EAB。
- [ ] 申请并保存 mTLS 私钥、证书和信任包。
- [ ] 证书和私钥不得提交到 Git 或作品公开链接。
- [ ] 在平台 Discovery 中搜索到注册智能体。
- [ ] 从平台发起访问并取得真实返回。
- [ ] 记录平台后台访问量和跨端互联日志。

### P2：其余智能体和验收链路

- [ ] 按同一流程注册采购智能体。
- [ ] 按同一流程注册跟单智能体。
- [ ] 按同一流程注册质量文档智能体。
- [ ] 验证 Leader → 报价 → 采购 → 跟单 → 质量文档的真实调用链，或记录实际采用的链路。
- [ ] 保留一次成功调用和一次失败/缺数据调用，证明系统会如实反馈限制。
- [ ] 页面、日志和报告中的 AIC、编号、时间和访问量保持一致。

### P2：比赛材料

- [ ] 作品名称不超过 20 字。
- [ ] 作品简介不超过 300 字。
- [ ] 技术方案导出为不超过 10 MB 的 PDF。
- [ ] 验收视频为 MP4，时长 3—5 分钟，大小不超过 300 MB。
- [ ] 视频完整展示梧桐平台注册、发现、互联、访问流程。
- [ ] 答辩 PPT 导出为 PDF。
- [ ] 佐证材料合并为一个 PDF。
- [ ] 完整代码、一键部署文件和大型材料放入百度网盘链接。
- [ ] 作品方案、视频和 PPT 不出现学校名称、学校 LOGO 或指导教师信息。
- [ ] 技术报告附平台访问量截图、互联交互日志、测试原始数据和代码改造说明。

## 6. 每一步的完成证据

一个任务只有同时具备以下证据，才可以改为“已完成”：

- 实际平台页面或 API 响应；
- 真实状态、AIC、编号或时间；
- 服务端调用日志和任务链路；
- 必要时的页面截图或录屏；
- 对失败、不可达、缺数据和证书问题的明确结果。

本地测试、静态 ACS 文件、Mock 数据和 `TBD-*` 占位值，都不能作为梧桐平台注册成功或跨端互联成功的证据。

## 7. 交给后续 AI 的第一句话

先阅读本文件、`docs/AI_HANDOFF_PLAN.md`、`docs/current_status_and_fix_plan.md` 和四个 ACS 文件；先只读确认 Leader 入口、平台可访问 endpoint、provider 和证书边界，再提出最小实施方案。未知字段、未知平台接口和未知比赛数量不得猜测，必须停下并要求补充资料。
