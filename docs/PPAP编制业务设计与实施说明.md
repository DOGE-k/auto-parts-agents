适用项目：`E:\competition\汽车零部件工厂智能体开发`

用途：供后续开发者理解范围、核对输入、实施功能和组织验收。

## 1. 目标与已确认范围

第四个业务智能体仍为质量文档智能体。本阶段以 **PPAP 编制** 为主要职责：接收产品、客户、供应商、工艺、生产和检验资料，持续推进 PPAP 任务，生成可编辑的文件包，完成检查、人工审核和版本归档。

这项改造必须接入现有业务流程及跨智能体协作。仅增加一个填写表单后导出 Excel 的入口，或仅生成封面和附件目录，不满足目标。

用户已经确认：

1. 本阶段聚焦 PPAP；暂不开发独立的 8D、IMDS、常规检测报告业务模块。PPAP 本身需要的检验结果表、MSA、初始过程研究等仍属于 PPAP 范围。
2. 保留现有质量问题登记、NCR 处置、解决、关闭、关闭前置检查、质量影响分析和质量待办。
3. 保留现有项目登录、人工审批、真实系统写回、回读验证、幂等、审计及发运判断规则。
4. 保持报价、采购、跟单、质量文档四个业务智能体；沿用现有协调运行时，不增加第五个业务智能体。
5. 参考用户提供的采购侧资料学习结构、字段和版式；不能将其原始业务数据或已填写结论冒充本项目生成结果。
6. 新功能在验证通过之前保持“待实施”“待验证”状态，不能写成已经支持完整 PPAP 或已经满足认证要求。

## 3. PPAP 的业务对象与任务启动

### 3.1 主对象

任务以“客户 + 零件号 + 零件/图纸版本 + 提交要求”为核心对象。销售订单、采购记录、工单、生产批次和检验记录是关联依据，不代替零件版本与客户要求。

左右件可以组成一个资料包，但必须分别保留零件号、左右属性、规格、测量数据及适用文件。不能根据相近名称、相近时间或列表第一条自动匹配。

每个任务至少需要：

- 任务编号、业务对象及版本；
- 提交原因、客户模板和模板版本；
- 适用条目及客户提交/保留要求；
- 已确认的订单、工单及批次关联；
- 任务负责人、期望完成日期和当前进度；
- 输入快照、文件版本、检查结果和审查记录。

这里的“提交原因”和“期望完成日期”是用户/业务资料输入，不能推测为每张工单完工时都必须提交。

### 3.2 启动规则

一期采用已登录用户确认启动 PPAP 任务的方式，并预留业务事件接入点。具体客户触发条件、变更分类和自动创建规则，实施前核对。

可从关联订单/零件入口带入已知信息，也可从质量中心独立建立任务。自然语言问答可以解释需求、查询当前任务及提出启动建议；不能在未授权时直接持久化任务或批准结果。

任务启动后，系统自动编排已授权范围内的读取、分析、计算和未批准草稿生成，不要求用户逐项点击每一个取证步骤。

不是所有订单或工单都需要新建 PPAP。客户已有有效资料包时，应识别可引用的版本；是否重新提交由客户要求及适用变更规则决定。

## 4. 四个智能体如何协作

| 岗位 | 对 PPAP 的贡献 | 缺数据时的处理 |
|---|---|---|
| 报价及订单侧 | 客户、零件、产品要求、已确认的订单关联，以及有来源的技术资料 | 形成产品/客户要求待补项，不从报价金额推断工艺或公差 |
| 采购 | 材料、供应商、材料批次、供应商证明及提交资料的关联 | 指出缺哪份供应商证据；不把供应商名字当作试验报告 |
| 跟单 | 工单、工艺快照、试生产批次、生产及可关联的检验记录 | 数量和报工速率不能代替尺寸实测值或过程能力数据 |
| 质量文档 | 确定适用资料、组织取证、编制草稿、检查一致性、形成审核包 | 自动生成明确的缺项/冲突待办，记录需要的证据及责任岗位 |
| 人工工程输入 | 客户特殊要求、图纸、批准的工艺/质量基准、风险判断和审核决定 | 提示具体需要确认的事项，不生成未经确认的专业结论 |

工作流为：

1. 确认任务对象、客户要求与提交原因。
2. 第四岗形成资料要求和取证计划。
3. 协调运行时按数据需求调用前三岗及第四岗的分析技能，不机械强制每次都调用全部智能体。
4. 汇集接口结果、用户上传资料及人工确认信息；保存来源和版本。
5. 编制可完成的条目，计算有充分原始数据的结果；缺项和冲突单独保留。
6. 展示草稿、检查结果和待确认事项，允许人工修订。
7. 人工发起审核、批准或退回；批准后冻结该版本并归档。
8. 上游数据变化时标记影响范围，生成新的草稿版本或待修订任务，保留旧版。

没有现成接口的数据，可以通过受控导入取得。企业资料入口不应被“OpenMES 没有报告生成接口”阻断；项目自身负责文件编制和版本管理。

## 5. 自动编制内容及依据

### 5.1 客户条目模型

条目目录必须可配置，支持客户扩展以及“提交”“保留”“按要求提供”“不适用”及其依据。内部条目 ID 不依赖工作表顺序。

用户提供的客户样例包含扩展要求，不能硬编码为固定 18 张工作表。生产件样品、标准样件、检具等实物条目，应管理其记录和关联证据，不将生成一张表等同于已经提供实物。

### 5.2 编制方式

| 内容 | 编制方法 | 必要约束 |
|---|---|---|
| 提交清单、PSW、附件目录、变更履历、设备及包装表 | 从统一基础信息和有来源的业务记录填充客户模板 | 不复制旧样例的公司、零件、日期、人员、签字及结论 |
| 过程流程图 | 使用实际工序和经确认的工艺关系组织图表 | 工序不存在或未确认时标待补，不从产品照片猜工艺 |
| 特殊特性清单、PFMEA、控制计划 | 复用批准的工程基准及过程知识；模型辅助编制结构化草稿和待审建议 | 评分方法、评级和控制措施须有依据；不能直接套用其他零件的 RPN 或优先级 |
| MSA、初始过程研究 | 通过经确认的方法及原始数据确定性计算，再填充结果表 | 模型不生成测量数值；算法、单位、样本布局和适用条件要明确 |
| 尺寸、材料和性能结果 | 从原始检验/试验数据及规格填表，保存记录关联 | 空值、缺报告和不适用必须区分；不能填“合格”来补缺口 |
| 图纸、实验室资格、客户工程批准等 | 引用或归集原始文件及有效版本 | 不自行生成原始工程批准、资质或签名 |

一期必须包含实质编制能力：至少贯通过程流程、特殊特性、PFMEA、控制计划，以及输入满足条件时的 MSA、过程研究和尺寸结果表。只有目录、封面和文件拼接属于部分实现，不能认定整体完成。

模板支持分阶段上线。先选定一套客户模板完成整条流程，再扩大模板适配范围；不能将尚未确认的模板或计算方法强行补齐为完成状态。

### 5.3 数据一致性检查

至少检查：

- 零件号、左右属性、名称、材料、重量、图纸/工程版本与日期是否一致；
- 工序、特殊特性及测点编号在流程图、PFMEA、控制计划、检验表中是否对应；
- 单位转换、规格上下限、测量值和最终结论是否一致；
- MSA 评价人、零件数、重复测次及完整性是否符合选定方法；
- 过程研究样本范围是否正确，是否混入汇总值、缺样本或存在公式错误；
- 不同零件或不同版本的检验数据是否被混用；
- 必需证据、客户确认或审核条件是否缺失；
- 模板公式、外链、嵌入对象及打印布局是否得到正确处理。

检查结果记录严重程度、受影响条目/字段、依据和处理状态。不能用“错误数为零”替代“完整资料已读取”的证明。

### 6.2 从样例学习到的约束

1. 文件存在多张表和客户扩展目录；有的资料为空，不能按目录出现就算齐全。
2. 可能有历史零件名称、版本、重量、单位和日期残留；重复字段需要统一来源。
3. 存在公式缓存错误、样本范围不一致和计算结果与手工结论冲突；不能直接复制公式为生产计算规则。
4. 部分测量表使用随机公式或缺少原始数据；这类值不能作为真实检测证据。
5. 存在嵌入公式对象、普通图片、WPS 单元格图片及历史外部链接。只按单元格文字读取可能遗漏内容；不执行宏/OLE，不自动刷新未知外链。
6. 部分签字栏未完成；有人名或日期不等于客户批准。

应先形成清理后的模板、字段映射及适用条目表，再接入生成。必要时以原文件为受控参考，制作新的干净模板；遇到无法保留的原生格式或对象，应明确报告，而非静默删除。

## 7. 数据、版本与证据设计

建议按以下概念组织模型，具体表名/API 名称由实施者结合现有架构决定，下面不是已存在接口：

| 对象 | 主要职责 |
|---|---|
| PPAP 任务 | 业务对象、客户要求、范围、负责人及进度 |
| 客户模板版本 | 表格、字段映射、条目、规则及打印布局 |
| 证据记录 | 来源系统/文件、记录 ID、页码或表格范围、版本、内容摘要、哈希及核对状态 |
| 结构化工程与检验输入 | 原始值、单位、规格、来源及人工确认；支持左右件及测点分离 |
| 编制运行 | 输入快照、执行步骤、调用链、模型/规则/模板版本、失败与重试 |
| 文档条目及产物版本 | 编制内容、来源引用、检查结果、文件位置及版本关系 |
| 缺项/冲突任务 | 缺什么、影响哪项、责任岗位、处理状态和补录依据 |
| 审核记录 | 项目用户、意见、批准/退回的具体产物版本及输入快照 |

要求：

- 新模型使用数据库迁移；不通过删除数据库重建，也不把真实 PPAP 任务挂到合成场景专用记录上。
- 文件和结构化数据采用可恢复存储；实际目录与下载授权由部署配置确定。数据文件不放进源代码目录。
- 同一输入快照、模板和算法的重复编制请求需幂等；重复业务事件不得生成多份相同待办。
- 读取远端列表必须有完整分页或明确范围；截取前若干条不能宣称取得全量证据。
- 上游 401、超时、解析失败与合法空结果分开展示，不能转换为“没有问题”或“资料齐全”。
- 批准版本不可被后台更新覆盖；变更生成新草稿，旧版本保留。
- 导出文件应与批准/审阅的产物版本一致，记录可核对的版本及内容指纹。

## 8. 任务流程、授权与自动运行

### 8.1 分开管理四类状态

1. 任务运行：待启动、运行中、等待资料、失败、完成。
2. 文档条目：待资料、可编制、已生成草稿、存在冲突、待审核、已审核、不适用。
3. 包审核：未提交、审核中、退回、内部批准、已归档。
4. 客户处理：未提交、已提交、客户退回、客户接受等，仅在取得实际记录后登记。

这些是业务语义建议，不要求硬编码中文状态名。任务运行完成不等于内部批准；内部批准不等于客户接受；PPAP 审核不等于 NCR 已关闭或允许发运。

未齐全的工作草稿可以供编辑或下载，但必须明确列出缺项和冲突。必需资料、适用性或审核阻断项未满足时，不允许标记为批准；真实检测结果不符合规格时也不能用完整性检查替代专业处置。

### 8.2 兼容现有只读能力目录

当前 `capability_catalog.py` 只接受 `read_only=True`、`requires_approval=False` 的技能；真实 AIP 表面也按此目录限制。问答协调者不能直接保存文件、修改任务或执行审批。

一期建议：

- 问答/AIP 查询侧提供 PPAP 要求分析、取证计划、只读预览、缺项解释、状态和版本查询。
- 已登录用户通过受控接口确认启动任务、上传/确认输入和请求编制。
- 后台工作流在授权任务范围内读取真实资料、调用分析技能、计算并保存未批准草稿；所有状态变更记录任务授权来源。
- 人工审核、批准、归档与后续修订通过身份/权限校验的操作完成。
- 工作流自动更新限于已启动任务的草稿范围；没有任务授权或超出业务对象时停止并提示。

保存草稿、注册文件和变更业务状态不是只读操作。不能将生成接口强行标成只读来进入目录，也不能直接放宽整个目录的写入限制。若确需让 AIP 直接承载受控写技能，应另行设计认证、授权、策略隔离和审计，不能以本次 PPAP 名义绕过现有门禁。

项目已有 `quality_manager` 权限。新增操作应显式声明权限并复用项目身份；不得信任请求体中自填的审批人。持久化 PPAP 操作至少要求项目登录；细分岗位权限和可访问对象在实施前核对并写入权限表。

## 9. 现有质量功能如何保留

| 现有能力 | 本阶段处理方式 |
|---|---|
| 质量问题登记及登记审批 | 保留接口、权限与回读；作为相关 PPAP 问题证据来源 |
| NCR 处置、解决、关闭及前置检查 | 保留完整流程，不因加入 PPAP 合并或跳过审批 |
| 质量影响分析、质量待办、协同事件 | 保留；新增 PPAP 查询不替代原有响应 |
| 项目登录和审批审计 | 继续沿用；PPAP 审核记录独立指向文档/包版本 |
| 现有质量和发运判断 | 保持当前规则；不自动增加“所有 PPAP 批准后才可发运”条件 |

关联的质量问题及其处理状态可以影响某条 PPAP 证据的审查，但哪些状态阻断 PPAP 内部批准，需要按客户/业务规则明确。不能一律用“问题已解决”或“NCR 已关闭”替代全部 PPAP 审核，也不能用文件生成绕过质量门禁。

如果以后需要在发运判断中增加 PPAP 条件，应另行确认适用范围、客户例外和已有订单的迁移方式，不属于本次已授权规则变更。

## 10. 前端与问答体验

质量中心提供两个清晰入口：

- **PPAP 编制**：任务列表、业务对象、资料准备、编制进度、缺项/冲突、文件审核和版本归档。
- **质量问题处理**：沿用现有质量待办、NCR 处置与协同事件。

PPAP 详情应回答：对应哪个零件和版本、为什么需要提交、哪些资料已经取得、缺什么及由谁补、文件生成到哪一步、哪些内容需确认、当前审阅的是哪个版本。

主要操作包括：从业务对象启动任务、导入/确认资料、请求编制、处理缺项、查看来源、修改草稿、提交审核、批准/退回、导出指定版本。页面刷新后恢复进度，不靠浏览器内存保存唯一状态。

现有业务上下文可带入，要求精确关联和显式确认。上传、模板配置与人工补录是资料接入手段，不把整个日常流程退化成反复手填模板。

问答应能够回答“这个零件的 PPAP 还缺什么”“为什么不能提交审核”“这个版本改了哪些表”“材料证明来自哪里”，并可定位对应任务。若用户提出编制请求，应提供受控启动入口或确认单，保留真实调用链。

## 11. 建议实施顺序

### 阶段 A：资料与契约确认

- 复核本文范围、现有代码及资料访问路径。
- 整理一套客户模板的条目与字段映射，清除旧业务值，识别公式/图片/外链等原生对象。
- 确认数据字段来源、单位、左右件及版本关系，核对真实 ERP/MES 可用接口。
- 建立“已确认/缺数据/需要业务确认”的清单；关键未知项不凭经验猜测。

产出：模板映射、输入契约、计算方法及权限/审核规则的确认清单。

### 阶段 B：业务任务与自动取证

- 数据模型与迁移、任务启动及授权。
- 对接现有业务对象和真实只读技能；实现来源记录、缺项待办与工作流状态。
- 展示质量中心 PPAP 任务及进度，保持既有质量功能可用。

产出：可恢复、可追溯的任务与取证链路。此阶段不能宣称已实现整包编制。

### 阶段 C：实质编制与导出

- 统一基础信息、工序、特性和检验结构。
- 模板填充、工程草稿编制、确定性计算和跨表检查。
- 生成可编辑 Excel、缺项/冲突清单和来源索引；核对图片、公式和打印布局。
- 有效输入得到实际内容；缺失输入明确阻断受影响条目。

产出：所选模板范围内可审阅的 PPAP 草稿包，不是只有封面和目录。

### 阶段 D：审核、变更及完整验收

- 版本审核、退回、批准、归档及源数据变化后的影响分析。
- 问答状态查询及业务跳转。
- 新旧流程回归，运行有明确来源的业务验证；更新功能与部署文档。

产出：所选模板的任务启动 → 自动取证 → 编制 → 缺项处理 → 审核 → 归档闭环。扩大其他模板覆盖作为后续逐项验收，不虚报所有客户均支持。

## 13. 验收标准

| 编号 | 必须验证的行为 |
|---|---|
| AC01 | 针对明确客户、零件及版本启动任务，订单和工单关联有依据；左右件不混用 |
| AC02 | 已启动任务自动读取可取得的真实资料，保存来源，产生真实调用链，而非每个字段都靠手填 |
| AC03 | 缺项显示具体资料、影响条目和补充岗位；接口错误、空数据及不适用可区分 |
| AC04 | 产品基础信息复用到不同表；更改材料/规格等后识别受影响条目，不遗留旧值 |
| AC05 | 流程、特殊特性、PFMEA、控制计划与检验测点可关联；工程草稿有依据及待审核状态 |
| AC06 | MSA/过程研究使用原始数据与确认方法，和独立计算对照；缺样本、异常单位、零变差等边界可正确暴露 |
| AC07 | 尺寸/材料结果源自已关联记录，禁止随机生成实测值、伪造报告或自动补“合格” |
| AC08 | 导出 Excel 有实际内容、可编辑；重要表格、图片、公式及打印布局经实际查看验证 |
| AC09 | 重要缺项/冲突阻断批准；内部批准、客户接受、NCR 关闭与发运判定不混同 |
| AC10 | 批准对应具体文件及输入版本；修改形成新版本，批准版不被覆盖 |
| AC11 | 匿名用户不能持久化编制任务或审批；身份来自项目会话，文件访问有授权，问答目录不开放未授权写入 |
| AC12 | 重复请求和事件幂等；失败可定位、受控重试；刷新页面后任务和审查进度可恢复 |
| AC13 | 已有质量登记、处置、解决、关闭、人工权限、回读、审计及发运规则通过回归 |
| AC14 | 编制与查询经过第四岗及现有协调运行时；不能只有前端导出或未实现的技能名称 |
| AC15 | 问答可解释缺项/变更/证据并定位 PPAP 任务；无相关对象时澄清，不借用其他订单 |
| AC16 | 代码仓库不包含原始企业资料、凭据和真实生成包；测试数据标识清楚，部署可迁移并说明文件备份位置 |

测试使用隔离数据库和明确标识的输入；不以随机测量数据充当真实业务验收。改动范围内运行后端测试、前端测试、类型检查、构建及格式检查；真实 ERP/MES 与实际 Excel 的验证结果单独记录，未执行的明确说明。

## 14. 实施前必须澄清的业务事项

以下事项尚未得到本次会话的具体确认，不能由实施者自行编造：

1. 第一套正式采用的客户模板及条目适用规则，生成对象所属的业务场景。
2. 产品/图纸/工艺/材料基准、实际原始检测数据，以及它们的确认责任。
3. MSA、过程能力和风险评级的方法、阈值、样本要求及版本。
4. PPAP 的客户提交原因、自动触发规则，以及已有有效包的引用/重新提交策略。
5. 哪些质量异常或偏差影响内部审核、是否存在客户批准的例外。
6. 岗位权限、审核人员及是否需要编制人与审核人分离；不能把当前单一账号结构擅自升级为已满足岗位分离。
7. 文件访问、备份、保存期限及客户处理记录的取得方式。

接手者先完成代码核对、资料盘点和不依赖上述答案的基础设计，再一次性提出关键问题。必要输入缺失时停下相关编制或业务规则，不停止可独立推进的工作。不要再询问是否保留质量审核、是否只做 PPAP 等本次已确认事项。
