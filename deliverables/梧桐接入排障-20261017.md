## 2. 根因（一句话）

旧版 `scripts/start_wutong.sh` 用 `subprocess.Popen(...)` **不传 env**，进程原样继承启动 shell 的
环境变量；运行期 `load_dotenv(override=False)` 又让**已存在的环境变量优先**。
14:08 启动时 shell 里有旧的 `DEEPSEEK_API_KEY`（含非 ASCII），`.env` 虽在 01:25 已改成 ASCII 密钥，
却始终未被采用 → 每次模型请求都在 httpx 编码 `Authorization` 头时抛 `UnicodeEncodeError`
→ 平台只显示「技能执行失败，请检查服务日志」。

这也解释了为什么密钥文件正确、`--live` 返回 HTTP 200 却仍失败：
只读文件的诊断脚本看不到进程继承的环境变量。

**证据**：`.env` 改于 01:25:04，进程起于 14:08:43；14:32 失败栈停在
`httpx/_models.py:156 _normalize_header_value`；`leader.log` 仅 44 行且断在栈中间。

**已生效的修复**：16:55 执行 `stop` → `unset DEEPSEEK_API_KEY` → `start`，
进程环境不再含该变量，`load_dotenv` 只能采用 `.env` 的值。

## 5. 梧桐平台登录失败（另一件事，与本故障无关）

平台**没崩**。实测：首页与 `openapi.json` 均 HTTP 200；登录接口连续 3 次错账号返回 401
而非 429（未限流）；`verify-code` 返回 200；服务器时间与本机 UTC 一致。

用假密码探测不同用户名，平台返回两种不同错误：

```
[不存在的用户名] 401 {"error_name":"USER_NOT_FOUND"}
[DOGE]           401 {"error_name":"INVALID_CREDENTIALS"}
[doge]           401 {"error_name":"USER_NOT_FOUND"}
```

`USER_NOT_FOUND` 与 `INVALID_CREDENTIALS` 在后端是不同分支
（`registry-server/app/account/service_auth.py` 的 `authenticate_user`）。
你的 `DOGE` 命中 `INVALID_CREDENTIALS`，说明：**账号存在且 active、用户名大小写正确、只有密码不匹配**。

处理：

1. 用**无痕窗口**打开 <https://wt.ioa.pub/>（避免浏览器自动填充旧密码），用户名 `DOGE`，密码手动输入且为英文半角；
2. 若当初是手机号注册、没设过密码，改用「手机号 + 验证码」登录；
3. 点「忘记密码？」走验证码重置；
4. 重置也失败就把页面完整报错发我（不要发密码）。

不影响当前进度：叮当的修复不依赖网页登录，只有「改已通过的 ACS」或「新角色注册」才需要。
