# 现在请先做一件事：回叮当复测（16:58）

## 为什么大概率已经好了

你 16:55 执行的三条命令里，中间那条是关键：

```bash
bash scripts/stop_wutong.sh
unset DEEPSEEK_API_KEY        # ← 这一条
bash scripts/start_wutong.sh
```

服务器上的启动脚本（旧版）用 `subprocess.Popen(...)` **没有传 env 参数**，
所以五个接入进程**原样继承当前 shell 的环境变量**。

- 14:08 那次启动：那个 shell 里有旧的 `DEEPSEEK_API_KEY`（含中文），
  运行期 `load_dotenv(override=False)` 就**不会**用 `.env` 的值 → 每次请求 DeepSeek 都在
  httpx 编码请求头时抛 `UnicodeEncodeError` → 平台只看到「技能执行失败」。
- 16:55 这次启动：你 `unset` 之后再启动，进程环境里**没有**这个变量，
  `load_dotenv` 于是采用 `.env` 里的 ASCII 密钥 → 编码问题消失。

这就是为什么"密钥文件明明是对的、诊断脚本也显示 HTTP 200，却仍然失败"——
问题从来不在文件，而在**进程继承到的环境变量**。

## 附带发现：服务器上的启动脚本还是旧版

你 16:55 的输出里没有这一行：

```
[密钥] 来源=dotenv 长度=35 ASCII=True
```

而新版脚本**一定会打印**。说明 `scripts/start_wutong.sh` 仍是 `524e56f` 的版本，
之前 scp 上去的 bundle 应该是更早的一版（同名文件、内容旧）。

30 秒确认：

```bash
cd /home/ubuntu/apps/auto-parts-agents
git log -1 --oneline
grep -c '\[密钥\]' scripts/start_wutong.sh
git bundle list-heads /home/ubuntu/wutong-update-20261017.bundle
```

- `grep -c` 返回 `0` → 脚本旧版，需要重新上传 bundle 并 merge；
- `bundle list-heads` 哈希 ≠ `558b4e3…` → 服务器上的 bundle 旧，重新 scp 最新的那个。

> 注意：`git log -1` 可能显示某个中间提交（如 `49187f6`），
> 这只说明同步到一半，不影响当前复测——先把功能验通，再补代码。

## 新代码同步上去之后能多得到什么

| 能力 | 现状（旧代码） | 新代码 |
|---|---|---|
| 平台失败文案 | 只有「技能执行失败，请检查服务日志」 | 附带异常类型 + 脱敏消息 |
| 密钥来源 | 无法判断 | 启动时打印 `来源=dotenv/shellEnvironment 长度 ASCII` |
| 坏密钥 | 进程照常启动、调用时才崩 | **启动即拒绝**并写明来源 |
